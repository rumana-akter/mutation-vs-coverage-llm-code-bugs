# Reproducing Table IV — Test Adequacy Criteria vs. Fault Detection in LLM-Generated Code

Graduate research reproduction assignment (Professor Benoit Baudry): reproduce
**Table IV** of *"How effective are traditional test criteria at detecting
bugs in large language models generated code?"* (arXiv:2609.09315).

**Read this first:** the paper's replication package does not exist publicly
(it's a very recent preprint) — see `PLAN.md` Section 3 for the documented
search. This repository is therefore a **focused methodological
reproduction**, not a numeric reproduction: it implements the paper's
described FTR/FDR definitions and randomized criterion-guided sampling
procedure, validates them on a
hand-crafted synthetic example, and then exercises them on real HumanEval
tasks using Claude-generated (not the paper's) faulty code and tests. See
`report/report.md` for the full account, including how our numbers compare
to (and differ from) the paper's, and why.

## Scope of this reproduction

| | Paper | This repo |
|---|---|---|
| Benchmarks | HumanEval+, MBPP, BigCodeBench, NaturalCodeBench | HumanEval only |
| Fault-generating models | 5 (GPT-5-mini, GPT-4.1-mini, Claude-Haiku-4.5, Llama-3.3-70B, DeepSeek-v4-flash) | Claude Sonnet + Claude Haiku 4.5 (substitutes; see `PLAN.md` §9) |
| Faults evaluated | 6,066 | 8 real (from 40 attempted tasks, across 2 batches) + 2 hand-crafted synthetic |
| Mutation tool | not specified by the paper | custom `ast`-based engine (`src/mutation_utils.py`); see `report/report.md` §9 |

## Running everything

```powershell
# 1. Unit tests for the core library
pytest -q

# 2. Synthetic experiment (hand-crafted faults, validates the full pipeline)
python -m scripts.run_synthetic_experiment
python scripts\build_table_iv.py results\synthetic_raw_results.csv results\synthetic_table_iv

# 3. Real HumanEval+ pilot, batch 1 (uses the pre-generated artifacts under data/)
#    (optional - data/pilot_humaneval_tasks.json is already committed;
#    re-run this only if you want to regenerate it from scratch)
python -m scripts.prepare_humaneval_tasks
python -m scripts.run_experiment
python scripts\build_table_iv.py results\real_experiment_raw_results.csv results\real_experiment_table_iv

# 4. Real HumanEval+ pilot, batch 2 (controlled scale-up, 20 more tasks)
python -m scripts.run_experiment_batch2
python scripts\build_table_iv.py results\real_experiment_batch2_raw_results.csv results\real_experiment_batch2_table_iv

# 5. Combine both batches into one dataset and build the combined table
python -m scripts.combine_batches
python scripts\build_table_iv.py results\real_experiment_combined_raw_results.csv results\real_experiment_combined_table_iv
```

### Expected output files

- `results/synthetic_raw_results.csv` — 600 rows (2 faults x 3 criteria x 100 iterations)
- `results/synthetic_table_iv.csv` / `.md` — aggregated Table-IV-shaped summary
- `results/real_experiment_fault_selection.json` — which of batch 1's 20 tasks had a faulty candidate, and which one was selected
- `results/real_experiment_raw_results.csv` — 1,500 rows (5 faults x 3 criteria x 100 iterations)
- `results/real_experiment_table_iv.csv` / `.md` — batch 1's Table IV row
- `results/real_experiment_batch2_*` — the same set of outputs for batch 2 (20 more tasks, 3 faults, 900 rows), plus `real_experiment_batch2_run_metadata.json` (timeout value and counts used for that run)
- `results/real_experiment_combined_*` — both batches merged (2,400 rows, 8 faults)
- `results/real_experiment_per_fault_table.csv` — one row per selected fault (both batches), with difficulty, test count, timeout count, and FTR/FDR per criterion
- `data/scaleup_task_selection_record.json` — the fixed-seed (42) random selection record for batch 2's 20 tasks (eligible pool, seed, resulting IDs)

All numbers in these files were produced by actually running the code above
— none are copied from the paper or hand-typed.

## Known limitations (see `report/report.md` for full discussion)

- The automated pipeline selected 8 behavioral divergences across 40
  attempted HumanEval tasks (Claude Sonnet produced 0 faults across 45
  candidates on 6 tasks; Claude Haiku 4.5 produced all 8 cases used here,
  across two batches). A later semantic audit (`FINAL_RESULTS_AUDIT.md`)
  classified 5 of these 8 as clear genuine candidate faults, 1 (`encrypt`)
  as uncertain, 1 (`find_zero`) as a numerical-equivalence artifact, and 1
  (`valid_date`) as a benchmark/reference defect. This is far too small a
  sample to draw any statistical conclusion about HumanEval; it validates
  the pipeline and illustrates the paper's qualitative claims, nothing
  more.
- **2 of the 8 faults are measurement artifacts, not genuine candidate
  bugs** — `find_zero` (exact-equality comparison applied to independent
  floating-point root-finders that never converge to bit-identical values)
  and `valid_date` (the real HumanEval reference solution has its own
  operator-precedence bug). Both are reported transparently rather than
  excluded after the fact; see `report/report.md` §11-13 and
  `EXPERIMENT_LOG.md` Entry 14.
- Test oracles are represented as `{args, expected_output}` equality checks
  rather than free-form assertions (documented as assumption A2' in `PLAN.md`).
- The mutation engine is a small custom implementation (5 operator types),
  not an established third-party tool — the paper doesn't specify one, and
  established tools (`mutmut`, `cosmic-ray`) turned out to be architecturally
  unsuited to this experiment's repeated-resampling design (see
  `EXPERIMENT_LOG.md` Entry 3).
- Every candidate/reference call runs in a persistent, killable worker
  process with a 5-second timeout (added after a real generated candidate
  was found to infinite-loop — `EXPERIMENT_LOG.md` Entries 12-13); a
  `cloudpickle` dependency was added to support this.
- MBPP, BigCodeBench, and NaturalCodeBench are not attempted (Phase 8 of the
  assignment explicitly scopes the real-benchmark portion to HumanEval only).

## Assumptions / deviations (full list in `PLAN.md` §9 and `report/report.md` §15)

1. Claude (Sonnet, then Haiku 4.5) used as a substitute fault-generating LLM.
2. Test oracle simplification (A2').
3. Custom AST-based mutation engine instead of an established tool.
4. Reduced scope: HumanEval only, 40 tasks across 2 batches, 5 candidates/task.
5. Under-specified prompts are our own constructions, not Larbi et al.'s
   unavailable artifact.
6. Batch 2's 20 tasks were selected via a pre-registered, fixed-seed
   (`random.Random(42)`) sample — recorded in
   `data/scaleup_task_selection_record.json` before any generation began.
