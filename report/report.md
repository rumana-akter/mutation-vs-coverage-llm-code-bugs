# Reproducing Table IV — "How effective are traditional test criteria at detecting bugs in LLM-generated code?"

**Assignment:** Reproduce Table IV of arXiv:2609.09315 (Hamidi, Konstantinou, Degiovanni, Papadakis), for Professor Benoit Baudry.

**Status of this work, stated up front:** this is a **focused methodological
reproduction**, not a numeric reproduction of the paper's Table IV. The
paper's own faulty implementations, generated test pools, and five
fault-generating LLMs are not publicly available (confirmed by a thorough
search — Section 4 below), so the real-benchmark portion of this work uses
substitute artifacts generated by Claude models during this project. Every
result reported here was actually computed by running the code in this
repository; nothing is copied from the paper or invented.

---

## 1. Introduction

Software testing has long relied on a small set of adequacy criteria —
statement coverage, branch coverage, and mutation testing — to decide
whether a test suite is "good enough." These criteria were designed for,
and validated against, human-written programs and human-introduced bugs.
The paper this assignment asks me to reproduce investigates whether the
same criteria still mean anything once both the code under test *and* the
tests themselves are generated by large language models — the "vibe
coding" scenario in which a person supplies a prompt and never actually
reads what comes out.

The paper's headline result is stark: even when a test suite is carefully
selected to maximize a criterion's score, it triggers only 25-78% of the
faults studied, and it actually *detects* (via a passing/failing assertion)
only 0-10%. Coverage adequacy, in other words, is nearly decoupled from
fault detection in this setting.

## 2. Objective

Reproduce **Table IV** specifically: for each (benchmark, fault-generating
model) pair, the mean Fault Trigger Rate (FTR) and Fault Detection Rate
(FDR) achieved by test suites selected to be adequate under statement
coverage, branch coverage, and mutation testing, averaged over 100
randomized selection runs per fault.

## 3. Understanding of Table IV

Table IV is built from the paper's experimental protocol (Section V),
which composes several precise definitions (Section IV-A):

- **Fault Trigger** (Def. 1): a test `t` triggers fault `f` if
  `output(faulty_program, t) != output(reference_program, t)`. A suite
  triggers `f` if any test in it does.
- **Fault Trigger Rate** (Def. 2): the fraction of faults a suite triggers.
- **Fault Detection** (Def. 3): a test *detects* `f` only if it *also*
  triggers `f` **and** its own oracle/assertion actually flags the faulty
  output as wrong. A test can trigger without detecting if its assertion
  is missing, too weak, or simply incorrect.
- **Fault Detection Rate** (Def. 4): the fraction of faults a suite
  detects. Always `FDR <= FTR`.
- **Fault Difficulty** (Def. 5): `1 - (fraction of the full test pool that
  individually triggers the fault)`. The paper keeps only faults with
  difficulty >= 0.75 (triggered by fewer than 25% of the pool) as its
  "non-trivial" corpus.
- **Mutation Score** (Def. 6-7): the usual killed/(killed+surviving)
  ratio.

The protocol that actually produces each Table IV cell (Section V): for a
given fault and a given criterion, repeatedly draw a random test from the
fault's pool, keep it only if it strictly increases the criterion's score,
and stop once the selected subset matches the *full pool's* score. Repeat
this randomized selection **100 times**, record whether each of the 100
resulting suites triggers/detects the fault, and average. Then average
those per-fault rates across every fault in a (benchmark, model) cell.

This two-level averaging (average across 100 resamples *per fault*, then
average those per-fault rates *across faults*) is not obvious from a
literal reading of Definitions 2 and 4 alone (which define FTR/FDR for one
suite over a whole fault set) — it only becomes clear from Section V's
prose description of how the table is actually built. Getting this right
mattered for our own aggregation code (`scripts/build_table_iv.py`).

## 4. Experimental Setup

### What the paper used (Section IV)

Four benchmarks (HumanEval+, MBPP, BigCodeBench, NaturalCodeBench), five
fault-generating LLMs (GPT-5-mini, GPT-4.1-mini, Claude-Haiku-4.5,

## 5. Reproduction Method

The repository is organized so that the *definitions* (`src/metrics.py`),
the *sampling algorithm* (`src/sampling.py`), the *coverage measurement*
(`src/coverage_utils.py`), the *mutation engine* (`src/mutation_utils.py`),
and the *orchestration* (`src/fault_runner.py`) are each independent,
unit-tested modules, used identically by both the synthetic experiment and
the real HumanEval pilot. This was a deliberate design choice: if the
synthetic experiment (whose correct answer I can work out by hand) passes,
I have real evidence the same code is trustworthy on real HumanEval faults,
rather than hoping it happens to work.

## 6. Fault Triggering and Fault Detection

Implemented literally as Definitions 1 and 3 in `src/metrics.py`:
`TestOutcome.triggered` is `faulty_output != reference_output`;
`TestOutcome.detected` is `triggered and oracle_flags_error`. Exceptions
are captured as a comparable sentinel (`_Raised(exception_type_name)`)
rather than propagated, so a test whose faulty program crashes and whose
reference program doesn't is correctly counted as triggering.

One deliberate simplification (documented as assumption **A2'** in
`PLAN.md`): a generated test's "oracle" is represented as a single
`expected_output` value rather than free-form assertion code. A test
"detects" a fault when the faulty program's actual output differs from
this expected value. This is exact and safe to execute, and it preserves
the paper's central distinction: a test can trigger (its input reveals a
behavioral difference) while its recorded `expected_output` still matches
the *faulty* program's output — a wrong/weak oracle — so it does not
detect.

The synthetic experiment (`scripts/run_synthetic_experiment.py`) makes this
concrete with a hand-crafted boundary bug (a `grade()` function using
`score > 70` instead of `score >= 70`) and two tests on the *same* input
(`score=70`): one with the correct expected value `"C"` (triggers and
detects) and one whose expected value is `"F"` — matching the buggy
output — modeling an LLM that reasoned from the buggy behavior rather than
the spec (triggers but does not detect). Both are asserted directly in
`tests/test_synthetic_experiment.py`.

**A note on non-terminating candidates, added during a later controlled
scale-up:** while generating a second batch of Haiku candidates, one
generated implementation (a subtraction-based GCD) was found to
infinite-loop on a zero input. `call_and_capture` was hardened to run each
candidate/reference call in a separate, persistent worker **process**
(threads cannot be forcibly killed in Python) with a 5-second timeout,
returning a distinct `_TimedOut` sentinel rather than hanging the whole
experiment - non-termination is treated as part of the program's observable
behavior, not excluded from the study. Two `_TimedOut` instances compare
equal to each other (no observed divergence if *both* sides hang on the
same input); a `_TimedOut` is never equal to a normal value or to a raised
exception (those are different observable outcomes). See
`EXPERIMENT_LOG.md` Entry 12 for the full incident, the timeout value's
justification, and the regression tests added.

## 7. Statement Coverage

Measured with `coverage.py` 7.16.0, the standard Python coverage tool. For
each individual test, we run it under a fresh `coverage.Coverage(data_file=None)`
instance and record the set of executed statement lines via
`Coverage._analyze(file_path).executed` (statement coverage is monotonic
under test-suite union, so a subset's score is just the union of its
tests' individually-recorded line sets — computed once per test, reused for
every candidate suite `sample_test_suite` considers, rather than
re-running coverage.py per candidate subset). This method is
semi-private (leading underscore) rather than coverage.py's advertised
report-generation API, because that API is oriented at producing
human-readable reports for a whole project, not raw per-run line sets for
one function call — we verified the exact return shape interactively
against the installed version before relying on it (`EXPERIMENT_LOG.md`
Entry 4).

## 8. Branch Coverage

Measured the same way, using `coverage.py`'s branch-arc data
(`Coverage(branch=True)`, `Analysis.arcs_executed_set` for the arcs a test
hits, `Analysis.arc_possibilities` for the static denominator).

## 9. Mutation Testing

**The paper does not name a specific mutation testing tool or framework**
— it only cites general mutation-testing literature. Per the assignment's
instructions, this required us to choose and justify our own.

We first evaluated `mutmut` (installed and inspected — see
`EXPERIMENT_LOG.md` Entry 3) and found its design mismatched to this
experiment's needs: `mutmut` is a whole-project, CLI-driven tool
(`mutmut run`) that re-invokes pytest as a subprocess once per mutant. Our
protocol needs, for one small faulty function, to generate its mutants
*once* and then evaluate hundreds of different test-pool *subsets* against
those same mutants (100 resampling iterations per fault) — a subprocess
per mutant per subset would be far too slow.

We therefore implemented a small, transparent, `ast`-based mutation engine
(`src/mutation_utils.py`) applying standard first-order operators from the
mutation-testing literature the paper itself cites: Relational Operator
Replacement (`<,<=,>,>=,==,!=` swapped), Arithmetic Operator Replacement
(`+,-,*,//` swapped), Boolean Operator Replacement (`and`/`or` swapped),
numeric constant perturbation (`+1`/`-1`), and — added mid-project after a
real limitation surfaced (see below) — Return Value Replacement
(`return <expr>` mutated to `return True`/`False`/`None`). Mutants are
compiled in-process via `importlib`, so repeated scoring during sampling is
fast. This is real mutation analysis (real mutants, real execution, real
kill/survive determination), just implemented directly instead of via a
third-party CLI, for the performance reason above.

**A genuine limitation we found and fixed mid-project:** the first
real-benchmark fault we found (`how_many_times`, a one-line
`return string.count(substring)`) has zero comparison/arithmetic/boolean/
numeric-literal sites, so our original four operators generated **zero
mutants** for it — mutation score was then vacuously "already met" by an
empty suite, giving a nonsensical mutation FTR of 0.0 (worse than doing
nothing). We diagnosed this directly (confirmed `generate_mutants` returned
`[]`), added the Return Value Replacement operator specifically because it
applies to any return statement regardless of its contents, verified it
produced 3 mutants for that same function, reran the full test suite
(43/43 still passing — no regression on the synthetic example, which
already had comparisons), and reran both experiments. The real
experiment's mutation FTR for that fault went from 0.0 to 0.6 (correctly
back above branch/statement's 0.42). This is recorded in full in
`EXPERIMENT_LOG.md` Entry 9 and is, itself, an interesting finding: a
"reasonable" small operator set can still fail entirely on short,
return-only functions, which are extremely common in HumanEval-style code.

Per Definition 7's denominator (killed + surviving, i.e. excluding
equivalent mutants), we make no attempt at automatic equivalent-mutant
detection (an open, largely undecidable problem). Instead the "target"
score `sample_test_suite` aims for is always whatever the *full test pool*
achieves — exactly mirroring the paper's own "match the full pool's score"
protocol — which sidesteps needing to identify equivalence at all.

## 10. Randomized Sampling Procedure

`src/sampling.sample_test_suite` implements Section V's algorithm exactly:
shuffle the pool with a local, seeded `random.Random` (never the global
RNG), repeatedly draw a candidate, keep it only if it strictly increases
the running score, stop once the selection matches the full pool's score
or the pool is exhausted. It is generic over any monotonic `score_fn`, so
the same function drives statement, branch, and mutation sampling. Nine
unit tests in `tests/test_sampling.py` cover an empty pool, a single
required test, redundant tests, determinism under a fixed seed,
non-determinism across seeds, that the original pool list is never
mutated, and two "exhausted pool" edge cases — one where the target is
trivially already met, one where it is genuinely unreachable by any
incremental sequence of single-test additions (constructed adversarially
to confirm the loop still terminates rather than hangs).

### 11.5 Unexpected benchmark-ground-truth issues

Two of the 8 automatically-selected faults turned out, on manual
spec-level inspection, to say more about benchmark ground truth than about
candidate correctness:

- **`find_zero`** (difficulty 0.000, FDR=0.00 on every criterion): the real
  HumanEval reference and the selected candidate are both root-finding
  algorithms (bisection vs. Newton's method) that converge to slightly
  different floating-point approximations of the same true root (e.g.
  reference `-0.5000000000582077` vs. candidate exactly `-0.5`, for
  `xs=[1,2]`) — a residual of `5.82e-11`, identical in magnitude across all
  8 tests in the pool, and well within the precision the task's own
  docstring convention (`round(x, 2)`) treats as "the same answer." Every
  test in the pool triggers, purely because exact float equality can never
  confirm two independently-converging iterative computations agree
  bit-for-bit — not because the candidate behaves differently in any
  meaningful sense. **This is floating-point/tolerance noise, not a
  meaningful violation of the spec.**
- **`valid_date`** (difficulty 0.867, FDR=0.00 on every criterion): traced
  directly against the natural-language spec ("the number of days is not
  less than 1 or higher than 31 days for months 1,3,5,7,8,10,12"), the real
  canonical solution has a genuine, verifiable Python operator-precedence
  bug: `month in [...] and day < 1 or day > 31` parses as `(month in [...]
  and day < 1) or (day > 31)`, so the final `or day > 31`/`or day > 30`
  clause on each line is unconditional rather than scoped to that line's
  month list. This causes the reference to wrongly reject valid end-of-month
  dates such as December 31 and January 31 (both present in the generated
  test pool) — and, verified by a full brute-force scan against the literal
  spec text, 18 distinct dates in total across the year. All 5
  independently-generated candidates use a fixed per-month day table and
  are verified (programmatically, across all 12x31 month/day combinations)
  to agree with the spec with zero mismatches; the independently-generated
  oracle also sides with the spec on both affected pool entries. **This is
  a live instance of the exact "reference solution defects can cause
  misclassification" threat to validity the original paper names in its
  own Section VII** — not a shortcoming of any candidate or of our test
  generation.
- **`encrypt`** (difficulty 0.917, FDR=1.00 — *not* one of the two
  artifacts above, included here because it is the borderline case the
  audit flags as genuinely uncertain rather than clean): the real reference
  solution only rotates lowercase letters (its lookup table is
  `'abcdefghijklmnopqrstuvwxyz'`; any uppercase character falls through
  unchanged), while all 5 independently-generated candidates chose to
  rotate both cases. The spec text ("the alphabet being rotated... shift
  down by two multiplied by two places") never states or exemplifies case
  behavior — every worked example in the docstring is lowercase-only. We
  do **not** resolve this as a settled reference defect (unlike
  `valid_date`, where the spec text is explicit and the reference
  demonstrably contradicts it): whether "the alphabet" implicitly means
  "all letters, case-preserving" or "the specific 26-symbol lowercase
  sequence the reference happens to use" is a genuine ambiguity the spec
  leaves open. It is kept in every result view at face value.

Only `starts_one_ends` (a real off-by-one bug at `n=1`) is an uncomplicated
instance of the paper's phenomenon among batch 2's 3 faults; combined with
batch 1's 5, 6 of the 8 faults are genuine, unambiguous candidate defects
(Category A in `FINAL_RESULTS_AUDIT.md` Section 1).

## 12. Comparison with Original Table IV

The paper's HumanEval row (Table IV, one line per fault model) reports, for
example, mutation/branch/statement FTR of 0.393/0.450/0.385 for
gpt-5-mini, or 0.137/0.103/0.088 for claude-haiku-4-5, with FDR uniformly
in the 0.00-0.03 range across every HumanEval cell — moderate FTR, very low
FDR, and no criterion consistently dominating across benchmarks. **Our
reduced experiment does not replicate that numerical trend.** Views A, B,
and C above all show substantially stronger mutation-guided FTR and,
outside the two artifact-driven cases, substantially higher FDR than every
one of the paper's five HumanEval rows. We state this explicitly rather
than letting the higher numbers imply a stronger or contrary finding: the
two results are not measuring comparable populations, for reasons explained
below.

**What our experiment actually found, stated plainly:**
- FTR is high across nearly every one of our 8 faults (0.6-1.0), and
  mutation FTR is 1.0 for 7 of 8. FDR equals FTR for 6 of 8 faults, and is
  0.0 (with high FTR) for the remaining 2 (Section 11.5).
- Once those 2 are set aside (View C), FDR equals FTR exactly across all 6
  remaining faults and all 3 criteria — no trigger/detection gap survives
  semantic validation in this sample (Section 11.4).

**What the paper found:** FTR in the 25-78% range across benchmarks and
models, and FDR almost always in the 0-10% range *for the same reason
across nearly all 6,066 faults* — LLM-generated test oracles systematically
fail to assert the behavior their own test inputs already exercise
correctly (Finding 2, Section VI).

**Why the two differ, considered explicitly rather than asserted as
"expected":**

1. **Sample size and selection bias.** The paper's HumanEval numbers come
   from 520 faults (Table II), generated by 5 models across a 10x/
   temperature-0.8 budget per task. Our 8 faults come from 200 total
   candidates (100 per batch) across 40 tasks with one substitute model.
   Every fault we keep is, near-necessarily, one a small and
   deliberately-probing test pool can reveal at all — we have neither the
   volume nor the model diversity to also sample the paper's much larger
   population of faults that remain essentially untriggerable by any
   criterion, which is a large part of what drives the paper's low overall
   FTR.
2. **Oracle-generation scale.** Our pools (7-15 tests/task, one task
   reasoned about at a time) are far smaller than the paper's LLM-Plain
   pools (thousands of tests/benchmark). All 93 tests across our 8 faults'
   pools have a genuinely-correct oracle once checked against independent
   ground truth (`FINAL_RESULTS_AUDIT.md` Section 4); this is very likely a
   property of small-scale, single-task, careful test generation, not
   evidence that oracle quality is not a real problem at the paper's scale
   - our sample is simply too small and too differently generated to speak
   to that question either way.
3. **A substitute fault-generating model, not the paper's five.** Both of
   our floating-point/reference-bug cases arose specifically because we
   used real, unmodified HumanEval reference implementations (as the paper
   also does) combined with a model (Haiku) whose natural mistake patterns
   turned out to intersect with numerically sensitive or already-buggy
   tasks. This is a property of which 40 tasks we happened to draw and
   which model we used to generate code, not a property of the testing
   criteria being studied.
4. **Our own mutation testing tool.** The paper does not specify one
   (Section 9); ours is a small custom operator set. A different, more
   complete operator set could plausibly change mutation's exact FTR/FDR
   values, though probably not the qualitative pattern (see below).
5. **Three below-threshold faults mixed into View A.** `how_many_times`
   (0.6), `concatenate` (0.0), and `find_zero` (0.0) would all have been
   excluded under the paper's own >=0.75 difficulty filter; View A (unlike
   the paper's Table IV) mixes "hard" and "easy" faults together.

**Where our result does, cautiously, echo the paper's qualitative claims:**
on `count_up_to` and `move_one_ball` (batch 1), mutation-adequate suites
reach FTR 1.00 while statement/branch reach only 0.13 and 0.32
respectively - a substantial, mechanistically-explained gap (Section 6/11
detail) consistent with the paper's observation that mutation "generally
achieves the best results" on some benchmarks. We do not extend this to a
general claim that mutation "confirms" or "directly echoes" the paper's
overall finding, since the paper itself reports the differences between
criteria as small and inconsistent across benchmarks (Table IV, Section
VI) - our 8-fault sample is compatible with that framing (mutation
outperforms on some faults, ties on others, and the two FDR=0 cases are
not about criteria at all) rather than a stronger or contrary one.

## 13. Observations

- **`encrypt`: 5 out of 5 independently generated candidates made the exact
  same choice** — extending a lowercase-only rotation cipher to uppercase
  letters, a case never demonstrated in the task's worked examples. This is
  a genuine, reproducible pattern across independent generations, subtle
  and hard-to-trigger (only 1 of 12 generated tests happens to contain an
  uppercase letter) — exactly the shape of fault the paper's methodology is
  designed to surface. **A closer, spec-level audit (`FINAL_RESULTS_AUDIT.md`
  Section 1) found this case is less clean than it first looked, however:**
  the reference solution's own lookup table is lowercase-only, so the
  reference *itself* leaves uppercase letters unrotated, and the spec text
  never states or exemplifies what should happen to them. Whether this
  counts as "5 candidates share a blind spot" or "5 candidates and the
  reference disagree on genuinely unspecified behavior" cannot be settled
  from the spec text alone — we classify it as uncertain (Category D)
  rather than a clean instance of the paper's phenomenon, and report it
  that way rather than keeping the more flattering original framing.
- **Weaker models produce more (and more useful) faults than a strong one
  in a one-shot setting.** Claude Sonnet, one-shot and blind, produced
  0 faulty candidates across 45 candidates on 6 tasks (Entries 6-8). Claude
  Haiku, under an identical protocol, produced 12 faulty candidates across
  100 candidates on 20 tasks (Entries 9-10), yielding 5 distinct faulty
  tasks after per-task fault selection. This directly supports the paper's
  decision to pool five models of varying strength rather than rely on
  one.
- **Prompt under-specification, in our setup, mattered less than model
  choice.** Deliberately weakening 3 prompts (removing disambiguating
  examples/phrases) produced zero additional faults with Sonnet; switching
  to Haiku on the same 3 (plus more) prompts, unmodified, immediately
  produced faults. We would not have discovered this without trying both
  levers separately and reporting the null results honestly rather than
  quietly picking whichever worked.
- **Coverage criteria can coincide with mutation when the buggy branch
  happens to be structurally necessary to reach full coverage** (the
  `encrypt` case, where all three criteria hit FTR 1.00) — coverage
  adequacy is not *always* weaker than mutation, it depends on whether the
  fault's location happens to be forced by the coverage goal itself.
- **A "reasonable" mutation operator set can still miss real code
  entirely.** Discovering that our mutation engine generated zero mutants
  for a one-line return statement was not a hypothetical concern raised in
  a threats-to-validity section — it was a real bug that silently produced
  a nonsensical result (mutation FTR of 0.0) until we noticed it looked
  wrong and traced it back.
- **Exact output equality, applied to a numerically-iterative task, treats
  "correct" as "identical to one specific reference implementation's
  floating-point rounding path."** `find_zero` showed FTR=1.00 against
  every candidate we tried, not because any of them were wrong, but because
  no two independent root-finders converge to bit-identical floats. This is
  a genuine limitation of Definition 1 taken literally (`!=` on raw output)
  for this specific class of task, not a bug in our code - the paper's own
  benchmarks likely contain a small number of similarly numerically-defined
  tasks (e.g. floating-point outputs anywhere in HumanEval+/MBPP), and this
  same effect would apply there too under an exact-equality reading of
  Definition 1.
- **A benchmark's own reference solution can be the thing that's wrong.**
  `valid_date`'s real canonical solution has a verifiable Python
  operator-precedence bug, causing 5 independently-generated candidates
  (and the independently-generated oracle) to all agree with each other and
  disagree with the reference. Definition 1 has no way to distinguish this
  from "the candidate is buggy" - it is defined entirely in terms of
  disagreement with the reference, which is exactly the "clean program
  assumption" critique the paper itself inherits from Chekam et al. and
  discusses in its own Section VII.
- **The FDR<FTR gap, when it finally appeared in our data, did not look
  like the paper's finding.** Six of our 8 faults have FDR=FTR (correct
  oracles); the two that don't are the floating-point and reference-bug
  cases above, not instances of a "careless assertion." Finding this out
  required investigating each fault's actual reference/candidate/oracle
  values by hand rather than trusting the aggregate number - a smaller,
  fully-inspectable sample made that possible in a way the paper's 6,066
  faults would not.

## 14. Challenges Encountered

- **No replication package.** Addressed by a documented, exhaustive search
  (Section 4) before inventing anything, and by getting explicit user
  sign-off on every substitution before implementing it.
- **A strong model resists producing natural faults.** Three separate
  rounds with Claude Sonnet (original prompts, under-specified prompts, on
  two different task sets) produced 0/45 faulty candidates. This is
  reported as a real, negative finding (Entry 8) rather than hidden or
  worked around silently.
- **Zero-mutant faults.** Described above (Section 9) — found by actually
  inspecting a suspicious result rather than trusting the pipeline blindly.
- **Comparing JSON-decoded test data to native Python return values.**
  JSON has no tuple type, so a generated test's `expected_output` for a
  function returning `(sum, product)` arrives as a list. Fixed with a
  small recursive list-to-tuple normalizer (`normalize_for_comparison`)
  applied to generated test data before comparison — documented as
  assumption A2' in `PLAN.md`.
- **A test-generation subagent producing a subtly wrong oracle itself**
  (for `sort_array`, a generated expected value for a negative-number case
  did not match a careful hand recomputation of the stated popcount-based
  rule). We deliberately did not "fix" this — an imperfect LLM-generated
  oracle is precisely the phenomenon under study, and `triggered` is
  always computed against the real HumanEval reference regardless of any
  given test's `expected_output`, so this could only ever have affected
  that one test's contribution to FDR, not the correctness of the pipeline.
- **A real infinite loop, found before it could hang the scale-up.**
  Reviewing generated code for the second batch (rather than only running
  it) surfaced a subtraction-based GCD candidate that loops forever on a
  zero input. Confirmed the hang directly with a timeout-guarded probe
  (which itself had to be force-stopped, since a stuck Python thread cannot
  be killed). Fixed by executing every candidate/reference call in a
  separate, persistent worker *process* (killable, unlike a thread) with a
  hard 5-second timeout and a `_TimedOut` sentinel, agreeing on its
  comparison semantics before implementing them (two timeouts are treated
  as "no observed divergence"; a timeout against any other outcome is
  triggering). This is an execution-safety addition, not a change to any
  FTR/FDR definition.
- **That same timeout fix silently broke statement/branch coverage
  measurement.** `coverage.py`'s instrumentation is process-local; moving
  candidate execution into a worker process meant the parent's coverage
  tracer no longer observed anything, and branch/statement FTR/FDR silently
  collapsed to 0.0 on the already-audited batch. Caught by re-running that
  batch as a sanity check *before* trusting the new infrastructure on new
  data, rather than assuming a passing test suite meant the fix was
  complete. Fixed by instrumenting coverage *inside* the same worker
  process (a wrapper closure passed through the unchanged `call_and_capture`
  API), then re-verified the audited batch's numbers were restored exactly.
  Both incidents are recorded in full in EXPERIMENT_LOG.md Entries 12-13.

## 15. Simplifying Assumptions / Deviations

All of the following are also recorded, with full context, in `PLAN.md`
(Sections 6-9) and `EXPERIMENT_LOG.md`:

1. **Fault source (A1):** Claude Sonnet, then Claude Haiku 4.5, used as
   substitute fault-generating LLMs in place of the paper's five
   commercial/OSS models, via isolated subagent calls blind to the
   reference solution.
2. **Test oracle representation (A2'):** structured
   `{args, expected_output}` equality checks instead of free-form
   assertion code.
3. **Mutation tool:** a small custom `ast`-based engine (ROR/AOR/BOR/
   constant/RVR operators), not an established third-party library, for
   the performance/architecture reasons in Section 9.
4. **Scope:** HumanEval only (not HumanEval+'s extra tests, not MBPP/
   BigCodeBench/NaturalCodeBench), 40 tasks total across two batches (not
   the full 164), reduced generation budget (5 candidates/task, not 10x2
   prompt variants x5 models). Batch 2's 20 tasks were selected via a
   pre-registered, fixed-seed (`random.Random(42)`) sample of the remaining
   143 tasks, not hand-picked.
5. **Under-specified prompts:** our own constructions "in the spirit of"
   the paper's cited technique (Larbi et al.), not a reuse of that
   unavailable artifact.
6. **Aggregation:** Table IV's two-level mean (per-fault across
   iterations, then across faults) is followed exactly, per Section 3.

## 16. Threats to Validity

- **Sample size.** 8 real faults (across 40 attempted tasks) is far too
  small to draw any quantitative conclusion about HumanEval as a
  benchmark; it is only large enough to validate that our pipeline can
  find, classify, and evaluate real faults correctly, and to illustrate
  (not statistically test) the qualitative phenomena the paper describes.
- **Reference-solution correctness is assumed, and was found not to always
  hold.** `valid_date`'s real HumanEval canonical solution contains a
  genuine operator-precedence bug (Section 11/13). Definition 1 treats any
  disagreement with the reference as "the candidate is faulty," with no
  mechanism to distinguish a genuinely wrong candidate from a wrong
  reference - exactly the "clean program assumption" limitation the
  original paper itself inherits from prior work and discusses in its own
  Section VII. We did not exclude this fault after finding the reference
  bug, since doing so after the fact, once we knew which result we'd get,
  would be a worse threat to validity than reporting it transparently.
- **Exact floating-point equality is unsuited to numerically-iterative
  tasks.** `find_zero` shows FTR=1.00 against every candidate we tried
  because independent root-finders do not converge to bit-identical
  floats, not because any candidate misbehaves. This is a structural
  property of Definition 1 read literally, not specific to our
  implementation - any exact-equality reproduction of this paper's
  protocol would show the same effect on a numerically iterative task.
- **Single fault-generation model family.** Both Sonnet and Haiku are
  Claude models; the paper's cross-model diversity (OpenAI, Meta,
  DeepSeek, Anthropic) is not represented, so any conclusion about "model
  diversity mattering" here is limited to within-Claude-family strength
  differences.
- **Test pool size and generation cost.** Our pools (7-15 tests/task) are
  far smaller than the paper's (thousands per benchmark), which plausibly
  explains our much higher measured FDR on the 6 faults where it is
  meaningful (Section 12).
- **Mutation operator coverage.** Our five operators are a reasonable but
  incomplete set; a fault whose only distinguishing behavior falls outside
  ROR/AOR/BOR/constant/RVR would still show mutation FTR of 0, as
  `how_many_times` briefly did before the fix.
- **Execution-safety infrastructure added mid-project.** The timeout
  hardening (Section 6/14) was necessary and is documented in full, but it
  means the two batches' raw results were produced by two different (though
  behaviorally equivalent, and re-verified to produce byte-identical
  results on batch 1) execution paths. We consider this a non-issue given
  the verification performed, but note it for completeness.
- **No statistical testing.** The paper reports Wilcoxon/Vargha-Delaney
  significance tests (Table V) across thousands of faults; with 8 faults,
  any such test here would be uninformative, so none is reported.
- **One fault's classification is genuinely uncertain, not just two.**
  `FINAL_RESULTS_AUDIT.md` classifies `encrypt` as Category D (uncertain)
  rather than a clean semantic fault — the reference solution's own
  lowercase-only handling of the rotation cipher may itself reflect
  incomplete spec coverage rather than a stated requirement all 5
  candidates missed. It is kept, at face value, in every reported view.

## 17. What I Learned / Thoughts

Reproducing even one table from a systems-heavy empirical SE paper turns
out to hinge less on the headline algorithm (the sampling loop in Section
V is a dozen lines) and more on getting every supporting definition exactly
right — what "output" means when a program crashes, what the mutation
score's denominator actually is, whether coverage is measured against the
faulty program or the reference. Small ambiguities compound: I initially
assumed mutation testing should always outperform structural coverage
(matching my prior reading of the paper's abstract), and the zero-mutant
bug on `how_many_times` would have silently confirmed that prior if I
hadn't looked closely at *why* a number came out at exactly 0.0.

The most striking empirical lesson, though, wasn't about coverage criteria
at all — it was how much fault yield depends on which model generates the
code and how it's prompted, independent of the testing criteria being
studied. A single strong model can be strikingly hard to trick into
"natural" mistakes even under deliberate prompt ambiguity, while a weaker
model in the same family reliably reproduces textbook mistake patterns
(non-overlap counting, off-by-one boundary conditions, over-generalizing
untested cases). This is exactly the paper's own methodological premise —
pool multiple models of varying strength — and living through a null
result before understanding why it mattered made that design choice feel
earned rather than assumed.

## 18. Conclusion

This project reproduces the experimental methodology behind Table IV on a
reduced, independently generated HumanEval+ dataset. It does not, and does
not claim to, recover the paper's Table IV numbers — the artifacts needed
to do that (6,066 faults, five models' worth of generations, large
LLM-Plain test pools) are not publicly available and were out of scope to
recreate at full scale for a graduate assignment. What it does provide is
a working, unit-tested, end-to-end implementation of the paper's actual
method — the FTR/FDR definitions, the randomized criterion-guided sampling
protocol, real statement/branch coverage via `coverage.py`, and real (if
simplified) mutation testing — validated first on a fully hand-verifiable
synthetic example and then exercised on 40 real HumanEval tasks (across two
batches: an initial 20-task batch that was fully audited before being
trusted, and an independently-drawn 20-task scale-up run under the same
frozen protocol) with genuinely LLM-generated (Claude Sonnet and Haiku)
faulty code and tests.

The reduced experiment produced substantially different quantitative
behavior from the original study, particularly higher mutation-guided fault
triggering and higher fault detection. Given the small and different fault
corpus, these values should not be interpreted as contradicting or
confirming the original large-scale result. A final semantic audit of all
8 selected faults (`FINAL_RESULTS_AUDIT.md`), performed after data
collection was frozen, found that the inclusive result's trigger/detection
gap is fully attributable to two specific, individually-verified cases — a
floating-point tolerance artifact and a defect in the benchmark's own
reference solution, not a candidate defect — and that this gap disappears
entirely once those two are set aside as a sensitivity check, while the
inclusive result itself is preserved unchanged as the primary reported
number. We report the inclusive result, the paper-aligned subset, and the
sensitivity analysis side by side (Section 11) rather than picking whichever
looks most favorable, since distinguishing a real finding from a
measurement artifact — and being honest about which is which — is itself
part of what this reproduction set out to practice.
